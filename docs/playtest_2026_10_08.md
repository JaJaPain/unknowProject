# Playtest 2026-10-08

Findings recorded during play; fixes after Abe ends the test.

## 1. Every upgrade asks for plain "Ore"

**Abe:** all upgrades say "ore". They should start as silicate and work their
way up, with higher upgrade tiers asking for the rarer ore types.

**Research:**
- Upgrade tiers have a single `cost_ore` number
  (`GlobalState.gd`, the upgrade table around lines 38-58), and the goal
  card shows one "Ore" row (`UpgradeGoal.rows`), paid from banked ore of
  any type.
- Banked ore already keeps its types (`GlobalState.storage_ore_mix()`,
  `storage_ore_types`), and paying takes from that mix
  (`OreTypes.take`, GlobalState ~3047). So the store can already pay by
  type; only the costs and the card are generic.
- Ore types: silicate (default, common), water ice (fuel), ferrite, cuprite,
  thorium (`scripts/economy/OreTypes.gd`).

**Proposed fix:** each tier's ore cost names its type, climbing with the
tier, for example tier 2 silicate, tier 3 silicate and ferrite, tier 4
ferrite and cuprite, tier 5 cuprite and thorium (water ice stays for fuel).
The goal card shows one row per type ("Silicate 50", "Ferrite 40") with
hints on where each is found, and paying takes those types from the bank.
Check the economy sim and the systems' guaranteed ores so each tier's type
is findable by the gate class where that tier is affordable.

## 2. Undocking clicks at the start, not when the beam lets go

**Abe:** the undocking click should play when the tractor beam releases at
the end, not when undocking begins.

**Research:**
- `DockingTractorBeam.gd` clicks twice for the player's ship: when the beam
  is made (`_start_hum` calls `_click()`, the "takes hold" click) and when it
  is freed (`_exit_tree`, the "lets go" click).
- Undocking (`UIManager._push_out_of_berth`) makes a fresh beam to push the
  ship out, so it clicks as the push starts, then again when the beam is
  freed at the end. Abe hears the first one as "the undock click", in the
  wrong place.

**Proposed fix:** the undock beam skips its take-hold click (a flag on
`configure`, or a property set before it's added), so undocking gives one
click, when the beam lets go and the ship is released. Docking keeps both.

## 3. Scan Composition button shows with no rocks in range

**Abe:** the Scan Composition button should only show up if asteroids are
in range.

**Research:**
- The target window's "Scan Composition (C)" button
  (`UIManager.target_scan_btn`) is shown whenever the selected target is an
  asteroid (`UIManager` ~4493, set when the target changes), however far
  away it is.
- The scan itself only reads rocks within `OreScan.RANGE` (400 m) of the
  ship, so far away the button does nothing useful.

**Proposed fix:** show the button only while at least one ordinary rock is
within `OreScan.RANGE` of the ship (checked on the HUD's regular update, not
just when the target changes), whatever is targeted; hide it docked. The C
key follows the same rule.

## 4. Sell and Bank buttons don't update after turning in ore

**Abe (screenshot):** after turning in an ore mining job at Kaelen, the hold
shows 5 / 100 m³ but the dock buttons still say "Sell Ore (30 m³ -> 30 SC)"
and "Bank 30 m³": they imply you still have all the ore.

**Research:**
- The buttons' text is set by `UIManager._update_sell_button()` (which also
  calls `_update_bank_button()`), called from the dock menu's own actions
  (selling, banking, opening the menu).
- A delivered ore job takes its ore out of the hold through
  `GlobalState.remove_ore()`, which doesn't tell the UI, and the job's
  turn-in path doesn't refresh the buttons, so they keep the old amount
  until the menu is reopened.

**Proposed fix:** refresh the dock's sell and bank buttons whenever the hold
changes: a `cargo_changed` signal from GlobalState (remove_ore, deposit_ore,
add ore, sell, clear) that UIManager listens to while docked, so any path
that moves ore updates them, not just this one. Check pressing the stale
button can't sell ore that's gone (it should already re-read the hold).

## 5. Ore jobs should name the ore type, and it should be mined here

**Abe:** missions should also specify the ore type. It must be found inside
the system, unless it's a really hard mission, and those should name the
system to go and get it in. All of this in code, not the LLM: the LLM can
just say "ore" and the code puts the type in.

**Research:**
- Ore jobs come from several places: the public board's ore postings
  (`PublicBoardOfferBuilder.gd` ~155 and ~231; the "Coolant Needed" one
  has no ore type at all), agent and Kaelen contracts through the mission
  templates (`MissionTemplateRegistry.gd` ~128 and ~286), the chapter
  director (`ChapterNarrativeDirector.gd` ~177), and premise cards
  (`deliver_ore(ferrite)`, `PremiseMissionComposer.gd` ~84).
- `MissionAdapter` (~164) carries an `ore_type` when one is given, and the
  board's summary shows it ("35 m3 Ferrite"); with none, it says "Ore" and
  any ore counts.
- Each system has `GlobalState.system_ore_mix` (what its rocks are made of),
  and every asteroid field is guaranteed a couple of rocks of each ore in
  that mix (`Asteroid.guaranteed_ores`, SystemFactory ~416). So "an ore
  that is here" is already knowable in code.
- Premise cards name their own ore (`deliver_ore(cuprite)`), which can be
  an ore the system doesn't have.

**Proposed fix:**
- One code step, after any ore job is made (board, agent, Kaelen, chapter,
  premise card): pick its `ore_type` from this system's ore mix, seeded so
  it stays the same for that job. Water ice only where the job is about ice
  or fuel. A premise card's named ore is kept only if the system has it;
  otherwise a hard job (high difficulty or reward tier) sends you to a
  nearby system that does have it, and names that system in the job.
- Text: the LLM writes "ore"; code replaces it with the type ("bring 35 m³
  of ferrite"), in the job text, board summary and N.O.V.A.'s remarks. A
  `{ore}` token where a template has one.
- Delivery only counts ore of that type (`deliverable_ore` already takes a
  type).
- Pairs with finding 1 (upgrades by ore type): the same ore names, and the
  same ladder from common silicate to rare thorium.

## 6. Kaelen shows up at outposts

**Abe:** Kaelen should not be at outposts, only the major stations.

**Research (to confirm when fixing):**
- Kaelen's lounge card is meant to be main-station only:
  `UIManager._kaelen_lounge_available()` requires the station to be
  `GlobalState.get_primary_station()` (the "primary_station" group, else a
  node named "Station").
- The agent (Kaelen's job desk) is skipped at outposts when pre-caching
  (`UIManager` ~4941), and the dock menu comments say outposts have no
  agent; but the agent button and its availability check
  (`_agent_contracts_available_for_station`) don't test the station type
  themselves.
- Suspects: an outpost in the "primary_station" group in generated
  systems, or the agent desk / a Kaelen dock message reachable at an
  outpost. Reproduce at the outpost Abe docked at.

**Proposed fix:** one rule, `kaelen_here()`: true only at the system's major
station (never `station_type == "outpost"`), used by the lounge card, the
agent desk, her dock messages and handoffs. A smoke check: dock at an
outpost, no Kaelen anywhere.

## 7. A lounge rumour quotes the story plan ("Player finds a dead ship...")

**Abe (screenshot, lounge conversation):** the comms radio showed
"[Soft Warning - Story] Nakruilren Courier Union Lio Brannock has been
hearing the same warning from different crews: "Player finds a dead ship
with a valuable cargo manifest, only to be chased by a Reaver-class
hostile"". "Player?"

**Research:**
- The line is a "Soft Warning" lounge rumour (`StoryManager.gd` ~3257): it
  quotes `story_state["current_foreshadow"]` word for word.
- `current_foreshadow` is filled from the campaign bible's
  `opening_situation` (StoryManager ~245), a planning note the large model
  writes for the game, not for the player (it says "Player", and
  "Reaver-class hostile"), or later from a model reply (~2447). Neither is
  meant to be read aloud.
- The same rumour pool quotes other planning fields verbatim too:
  `pending_hooks` ("Open Thread") and `active_tensions` ("Local Pressure").
  `AmbientChatGenerator.gd` ~110 also reads the foreshadow.
- `UIManager._format_station_intel_line` (~8128) adds the "[Soft Warning -
  Story]" tag in front, a debug label shown to the player.

**Proposed fix:**
- Never quote planning fields to the player. Either rewrite them into an
  in-world rumour first (code template plus the small model, checked for
  "player", "NPC", "quest", "Reaver-class" and other game words, then the
  usual reserved-topic check), or drop those three candidates and keep the
  rumours that are written for the player.
- A guard on every lounge rumour and radio line: anything containing
  "player" (as a word), "NPC", "quest" or similar is rejected and logged.
- Drop the "[Title - Source]" tag from the line (keep the speaker's name).

## 8. A system message when you ask to dock

**Abe:** when you click Dock at a station, a system message should read
"Dock request submitted to X station/outpost".

**Research:** the Dock command goes through
`UIManager._command_selected_target("DOCK")` -> the target-command handler
(~11300), which starts the autopilot, shows the target marker and pre-loads
the station's content, but posts nothing to the comms radio until Dock
Control speaks on arrival.

**Proposed fix:** when a DOCK command is accepted for a station, post one
SYSTEM line to the comms radio: "Dock request submitted to <name>." using
the station's display name ("Kova Outpost", "Halden Main Station"), once per
command (not again if Dock is clicked twice on the same target).

**Addition (Abe):** after the request, the station replies, as text on the
comms radio only (no voice): "Docking request received. Assume standard
approach vector." or similar. A few code-written variants from that
station's Dock Control, a second or two after the request line, e.g.
"Docking request received. Assume standard approach vector.",
"Request logged. Hold the standard approach.", "Copy your request.
Standard approach, berth assigned on arrival." (all three approved by Abe;
the second shortened at his request).

## 9. The same mission twice in a row (water filters; also "Silicate Run")

**Abe:** got the exact same mission assigned twice in a row, in the second
system: two delivery missions for water filters to the same location.

**Research, the water filters (live log lines 1097 and 1244):**
- Both were "Courier: Water Reclaimer Filters" (DELIVERY_COURIER), accepted,
  completed (1158), then offered and accepted again. No model call made
  them: they are story agent jobs from `StoryAgentOfferBuilder.gd`.
- A story beat or thread becomes a courier job; its item comes from a
  fixed list by the beat's id (`_story_item_name`, ~620: "Water Reclaimer
  Filters" is one of ten), and its destination from the beat. So the same
  beat gives the identical job.
- Same pay too: both paid 220 SC (Abe), so the reward is fixed by the beat
  as well, nothing varies between the two.
- The beat wasn't used up when its job completed, so the next offer picked
  it again. Check where story agent candidates are marked done
  (StoryManager / StoryAgentOfferBuilder) and why a completed courier
  job's beat stays a candidate.

**Also, the same day, ore jobs ("Silicate Run"):**

**Research (live log, `user://logs/godot.log`):**
- The model titled agent jobs "Silicate Run" three times this session:
  Captain Dask (log line 411), Director Voss (546, accepted and completed),
  Captain Dask again (651, accepted right after). All DELIVER_ORE.
- The quest novelty guard (`scripts/persistence/NoveltyHistoryStore.gd`,
  `user://quest_novelty_history.json`) stores structural signatures only
  (objective shape), and agent/faction must be part of the signature, so
  two agents asking for the same ore job under the same title both pass.
  Titles and briefs aren't compared at all.
- Likely also feeds the title: the system's ore is silicate and the prompt
  says so.
- Also in the log: the second Silicate Run's Kaelen completion line was
  "Zero ore? Yeah, I'll take that for my zero cut", and "Kaelen completion
  ... abandonment selected" for a job that completed. Check whether the
  completion reaction reads the delivered amount after the ore has already
  left the hold (see finding 4).

**Proposed fix:**
- Story agent jobs: completing (or abandoning) one uses up its beat, so it
  is never offered again; a test that completes a story courier job and
  checks the next offer is different.
- The novelty guard also compares the last few accepted jobs' titles and
  objective (type + ore type + destination), across agents: a near-duplicate
  is regenerated, or rejected with a "pick something different" note like
  campaign titles (`CampaignTitleHistory`).
- Code-made ore types (finding 5) will vary ore jobs by themselves.
- Fix the completion reaction to use the delivered amount from the job, not
  the hold.

## 10. Tractor beam release click fails (my 2026-10-06 change)

Found in the same log, not reported by Abe: every time the beam is freed
the release click errors: "Parent node is busy setting up children,
add_child() failed" (`DockingTractorBeam._click`, line 86, from
`_exit_tree`), then "Playback can only happen when a node is inside the
scene tree" (line 88). So the release click often doesn't play at all.
Also "Lambda capture at index 1 was freed" once nearby.

**Proposed fix:** play the release click from the place that frees the beam
(UIManager's push/dock callbacks) or add the player with
`add_child.call_deferred` and play on `ready`; never from `_exit_tree`.
Fold into finding 2's change (one click, at the release).
